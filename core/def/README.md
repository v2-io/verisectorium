# core/def — the term definitions

One file per term, `<term>.md` with `-` where the term has `⸱`. There are no groups: terms that were once defined "in one breath" now cross-reference each other with `«…»`, and each file stands alone for a cold reader. Terms are nouns, defined in the singular; verbs, adjectives and states are either plain English defined within the noun they belong to, or the noun's declared **subtypes** (`‹promised›` «row», full name `«promised⸱row»`), which have no file of their own. If a subtype ever needs its own discussion, it is a term.

**The leading ```` ```kdl ```` block** (KDL 2.0; what `bin/defs` reads): one `term "name" pos=noun pl="-s"` node, with children `subtypes "a" "b"`, `synonyms "x"`, `avoid "word" "why"`, and `rel verb term="target" card="{m,n}" note="…"`, one line per target (`informal=#true` when the target is not a term); then `status provisional`, or `status decided by="steward-and-lead" on="YYYY-MM-DD"` once it is.

**Body**, in this order: `# «term»` with the one-line definition directly under it; an optional `## Intro`; `## Definition` or `## Definition(s)` (senses or elaboration, with the invariants as bullets under `### Invariants`); any free `## …` sections the term needs (a defining property, a worked case); `## Discussion` (why it is cut this way); `## Examples`; `## Working Notes` (required: what is deliberately left open, with a lean; what the term was adjudicated against). Working notes are the segment's inbox, not part of core.

**References** everywhere in core: `«term»`, or `«wording|def/term»` where the wording differs from the term enough to be ambiguous. The wording may be singular or plural (per `pl`) and possessive (`«veritoid's»`), as the sentence requires. A bare `«term»` is valid only while exactly one def defines it or the outline promises it. A subtype is `‹sub›` beside its «noun» on the same line, or alone when unique across the lexicon; `«sub⸱noun»` is its full name and always valid. Inside tables the pipe is escaped: `«…\|def/…»`.

`bin/defs check` verifies all of the above and that the outline's `def` column matches the files. `bin/defs dot`, `overview`, `terms` draw and read the terms in outline order. History of changes to core is in `core/log.yaml` and the commits, never in these files.
