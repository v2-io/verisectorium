## 1. live_docs in core-2's words, in one paragraph

A live_docs **store** is one verisectorium with a one-level practical model: the **doc** is both veritoid and segment (one claim, one file, id minted from the creation timestamp and never reused, a mutable `label` as its name), of one of eleven **types** (its kind), carrying four written **facets** (`intent`, `force`, `realization`, `imposed_by`) plus lifecycle `status`, with five typed **edges** written on the doc (`belongs_to`, `requires`, `relates`, `provenance`, `superseded_by`). The **influx** is an inbox → raw (immutable, outside the graph) → normalized reference doc (frozen, inside the graph, demoted on every surface) → extracted claims, each carrying a `provenance` edge to the reference doc. The **log** is a per-session write-ahead log of writes (not acts), collapsed at `session close` into one history entry per touched doc and one **review** file per session that a human signs; history and review are both projections of the WAL. The **ontology** is `TYPE_TABLE` in `model.py` (which facets each type requires, forbids, and which `requires` targets it expects) plus the skills' shared definition files. The **frontier** is `ldoc validate`'s warning list plus the open flags, computed on demand and never cleared by anything but repair. There is **no checkpoint**: every write is live the moment it lands, review never gates, and the store has no concept of a steady state. Judgment lives in 27 agent **skills** (prose procedures) over a deliberately dumb CLI; every skill fix is recorded in a per-skill ledger with the failure quoted and classed. Samuel is the sole committer; Claude agents (Opus 4.8, Opus 5.5, Fable 5.1) co-author the October commits.

## 2. Where live_docs chose differently on a question core-2 also faces

These are the findings I weight highest. The first three touch the machinery.

### 2.1 No steady time — and what four months of that looks like

**Verified.** live_docs' founding review decision (`20260616181719`, Review Post-Hoc): "A change is considered *blessed on creation* whether it has been reviewed or not. … Gating review would reintroduce the drift this system fights: changes would queue behind an approval step, the live store would lag reality." Cascade does not gate either; `incompatible` "does not stop the other writes." Validate reports; nothing consumes its output but a gardening pass someone chooses to run. `session close` blocks on exactly one thing (a revision without an author note) and `--force` overrides it.

What the store looks like today, measured: 0 validate errors and **397 warnings**; **31 of 76 reviews unsigned** by Samuel (the unsigned cluster in mid-July and nearly everything after 2026-09-16, including the 55-doc facets migration review `20261006192312`); **32 of 41 raw clippings show `⚠ DRIFT`** on `ldoc raw list` (referenced by docs but never flagged ingested, a mechanism added after most ingests and never backfilled); **225 of 277 docs render "Unattributed"** because the October migration set `intent` only where evidence was in hand (52 docs); 155 docs `realization: unassessed`. No open flags, no open sessions. The warnings are one class of owed thing (missing `intent`, missing why-chain edge, body over ceiling, prose links not edged) with a named clearer (`garden-densify`, `garden-refine`, `garden-decompose`) and no moment at which anyone must either clear or accept them.

Samuel saw this coming: WISH.md (2026-07-01), "Really emphasize that the review process is the main mechanism for keeping the human in the loop, and it shouldn't ever be skipped (though with the rework it will be easier to mechanically enforce)." The rework (sessions, July) made the *review* mechanical; it did not add a moment at which the owed set must be empty or accepted.

**Bearing on core-2.** This is the strongest field evidence I know of for the «checkpoint» as core-2 defines it: non-gating writes (work time) *and* a computed statement of whether the store is steady, with acceptances-with-reasons as the only other exit. live_docs has the first half and not the second, and its queues silt in exactly the way the frontier def predicts ("any marker of done becomes a target"; here there is no marker at all, so nothing is a target). Two cautions ride with it. (a) Samuel's reason for non-gating is also core-2's: "a gate that always defers becomes a ladder that never fires" — the checkpoint must never become a gate on *writing*, only on *claiming steady*. core-2 already says this; live_docs is the reason to keep saying it. (b) The debt here is invisible not because it is uncomputed (validate computes it in one second) but because **no surface a working mind passes through shows it**: `ldoc map` ends with the open-flag count and nothing else; `session close` prints the review id and path and nothing else (verified in `cmd_session`). The frontier being computed is not enough; the practical model has to put it where every episode starts and ends.

### 2.2 Standing is written, with evidence the engine checks for presence

**Verified.** live_docs has no acts. Every statement about a doc's standing is written by the author: `intent` (what the person did: requested / chosen / incidental), `force` (must / should / may), `realization` (realized / partial / planned / deferred / unassessed), `imposed_by` (environment / tradeoff / choice), `status` (living / deprecated / reference). The things it *computes* from the record are: per-doc history and the review (projections of the WAL), effective scope (union along `belongs_to` ancestry), churn (history length), integration counts at review mint, orphan/entry-point status, and the `⚠ DRIFT` cross-check (typed `ingested_at` against graph evidence).

The failure this produced is the one core-2's written/done/computed table exists to prevent, and live_docs met it in production (reconcile-changes ledger, 2026-08-12): a 19-doc reconcile "produced ten docs at `level: preference`/`requirement` for choices that were an implementer's own convenience — built, tested, committed, but never raised or reviewed by the user … user-stated claims were recorded weak/agent-attributed while a convenience built in their place was recorded strong/settled, inverting the record." Root cause named in the ledger: "nothing in the workflow checked for this."

Samuel's fix (October, the facets model) is a third thing that core-2's table does not name: **a written assertion whose admissible values are gated by written evidence the tool checks for presence, not truth.** `intent: requested|chosen` is refused by `ldoc new`/`set` unless `intent_basis` is present (`_refuse_facet_violations`, `intent_needs_basis`); the basis is "the person's words quoted, or a citation that locates them (session and date, review id, raw clipping id)" (`_shared/facets.md`). The evidence rule then lists what is *not* a basis: silence, a commit, a merged change, a review signature, the doc having a provenance edge (every new doc has one), an agent's generalization. Judged "per claim, not per batch."

**Bearing on core-2.** Three things.

- It is a concrete answer to the **steward attestation** gap, different from the one core-2 sketches. core-2 wants the steward's word to be an act by an attested actor; live_docs lets an agent *write the steward's word on the steward's behalf*, with the quote and its location, and then has the steward sign the session's review after the fact. In core-2's terms: the per-piece assertion on the "who stands behind this" dimension is written by proxy, carrying a bears-on-style reference into a ‹source› (the raw clipping), and the steward's one act covers the session. The weakness is exactly the one `facets.md` is fighting: nothing checks that the quote supports the claim, and the ledgers show agents stamping batches with one shared basis. The strength is that it costs the steward one signature per session instead of one act per piece, which is the recording-cost gap. Worth deciding on purpose rather than inheriting either.

- It is evidence for core-2's open item **"which assertions compare with warrants"** (dimension.md Working Notes). live_docs' facets are all content-scope in core-2's sense except `intent`, which is a claim about standing. The tool treats them differently: `intent` needs evidence; `force` and `realization` do not. That is the asserts-as distinction, found by practice.

- "Silence is not ratification" (`20260723223658`, a `must` constraint) and the evidence rule's "a commit, a merged change, or a review signature" are not a basis — this bears on the «checkpoint»: an acceptance or a signed review covering a session must not be read as raising any piece's warrant. live_docs found that agents read a signature as ratifying everything under it ("we have to do it this way because you said so"). core-2's checkpoint conditions should say explicitly that an acceptance is about the owed item and warrants nothing about content.

### 2.3 Acyclicity on the hierarchy, cycles allowed in dependency

**Verified.** `20260617144556` (Graph Cycles Are Legal): "`belongs_to` is acyclic (enforced by validate as a hard error) … `requires` may legitimately cycle and is NOT enforced acyclic. Two decisions can mutually depend on each other — each moot without the other — and that is normal and expected. Unlike code, `requires` is not load-ordered." Cascade handles cycles at run time by refusing to revisit a doc it already updated.

core-2 chose the reverse: the predicated-on graph "has no cycles. A cycle found is something cut too coarsely" (reference.md), and projections nest without a cycle rule because they are gathering.

How Samuel got there matters as much as where he landed (the 06-17 raw, his words): "I had used the term 'dependency' (when I was meaning more of an 'influence' or 'impact' web/graph) that part was made *into* a DAG, and since we had a DAG, the hierarchy didn't add anything else. So the part that was skipped was the 'web', but it was voiced as though it was the DAG that was deferred." The whole edge vocabulary was then derived by a behavior matrix ("name the type after what it does — forward cascade, reverse cascade, removal jeopardy, structural membership, acyclicity, target-outside-graph, lifecycle side-effect — collapse rows with identical profiles") and `relates` vs `provenance` survived collapse only after Samuel challenged it and the surviving differences were named (direction is the content; immutable fact vs current judgment; validate-enforced vs optional).

**Bearing on core-2.** For a theory store, acyclic support is right and core-2's reason is right. For a specification store (udon) or a decision store, mutual requirement among decisions is real, and "cut too coarsely" is not always the diagnosis. core-2's reference def already lets the ontology add kinds "and their behaviour," so the question is only whether "predicated-on is acyclic" is a core invariant or AAT's declaration. I lean that acyclicity is a property of the *support* reading (validity caps along it; a cap cannot be well-defined on a cycle) and not of dependence in general; an ontology that declares a dependence kind along which nothing caps may allow cycles. live_docs is the specimen that one real store needs that. Second, the method — derive the kinds from the behavior matrix and collapse identical rows — is a cleaner way to decide core-2's reference-kind list than the current "kinds so far." Three of core-2's six kinds (narrates, restates, bears-on) would want their rows filled in; I suspect restates and narrates differ only in what passes along them.

### 2.4 Contradiction is resolved at write time by comparing standing; detection, not propagation, is the gap

**Verified.** core-2's frontier lists violations of declared relations: stale, dangling, unmet, broken, raised, overclaim. Two living pieces that contradict each other are not on it unless someone records a finding or a `restates` reference ties them. live_docs puts contradiction at write time and resolves it by rule (`_shared/conflict-test.md`, `facets.md` "The comparison"): "A doc that contradicts the new claim is **stale, not in conflict**, unless it states the same claim at a higher intent than the change carries." Same claim and change-intent ≥ doc-intent → update the doc, assertion included; below → leave it, write the new claim beside it as its own doc, `relates` them, name both in the report. "Neither row refuses, pauses, or asks permission." Different claims ("I want abc" beside "we should build xyz") → two docs, related.

And the finding that sits under it, promoted to a principle after a dogfood post-mortem (`20260626214249`, Detection Is the Supersession Gap): "Propagation — cascading updates along edges once a stale doc is identified — is the well-understood half of consistency. The failure in practice is upstream of it: the stale doc is never *retrieved*. … A doc whose wording predates a new vocabulary is invisible to a query phrased in the new terms." Remedy: reason over the `belongs_to`/`scope` neighborhood of the change, doc by doc; and "a system-changing initiative that supersedes *zero* existing docs is almost always a detection miss, not a conservative win" (`map-concepts-to-docs` carries this as a sanity check on the verdict map).

**Bearing on core-2.** The frontier is exactly as complete as the references, and live_docs' production experience says written references are systematically incomplete in the direction that matters: the dependency nobody wrote because the two pieces did not share vocabulary. core-2 names the predicated-on graph as the thing that carries consequence; live_docs' practical model adds a mandatory judgment walk over the *neighborhood* (projection membership plus scope zone) on every substantive change, and then `garden-densify` to turn what the walk found into edges so cascade can reach it next time ("A doc graph only self-heals where edges exist"). Two things for core-2's practical model: the reviewer of a changeset wants a default read set that is the segment's projection-neighbors and not only its referents; and a changeset that touches a root and lapses nothing should be treated as suspicious, which is the mirror of core-2's "if the frontier keeps growing, stop." Whether "two living claims contradict" should be a frontier item in the machinery is a real question; live_docs' answer (standing order decides, lower one written beside) is one the theory regime would reject (a flat contradiction between two exact claims is a broken check, not a ranking), but the spec regime might want.

### 2.5 One level of grain, and the claim is the title and summary

**Verified.** live_docs has no sub-doc addressing: refs resolve `id | label | unique title substring`; body wikilinks are bare `[[id]]`; the review's `touched` list, cascade verdicts, integration counts and history are all at doc grain. The reading rule that follows is in the `reference` skill: "A doc's claim is its title and summary. When only a body sentence supports your statement, say that it is one sentence in the doc's body, because body sentences drift from the claim the doc is about." The whole write discipline keeps a doc at one claim (body ceilings per type, 8 paragraphs / 400 words for a decision, warned by validate; `garden-decompose` splits; the hot-file signal, history length ≥ 5 with mixed summaries, is the churn-side detector of a doc carrying two claims).

**Bearing on core-2.** This is the practical form of core-2's open question "exactly two levels (veritoid, segment)." live_docs runs at one level and pays for it in two currencies: the splitting discipline has to be enforced by prose and gardening because the model cannot represent a step inside a claim; and the only sub-doc structure it has, the `## Implementation` section, had to be made a special exempt zone (volatile, "never a truth claim", excluded from the body ceiling, refreshed by `sync-realization`) because the doc could not hold a piece of different standing. That exempt section is a veritoid of a different kind living inside a one-veritoid segment, without the machinery to say so. core-2's two levels are what that section wants. Also worth taking: "the claim is the headline" matches core-2's projection-review rule (a review of a chapter reads each member's headline and assertion, not every step), and live_docs makes the headline a maintained field (`summary`) rendered verbatim on every surface rather than something read off the body.

### 2.6 Expected references live on the kind, not the instance

**Verified.** `TYPE_TABLE` gives each type its `expected_requires`: a use-case expects a goal; a principle or requirement expects a goal or use-case; a decision expects a norm or purpose; a component expects a decision, norm or purpose; `imposed_by: tradeoff` expects the decision or component it follows from. A doc with none of its expected targets upstream gets a validate warning, and `garden-densify` works that list "loudest first": "a norm with no goal or use-case above it is the loudest gardening signal: it is a rule nobody can weigh." The rule for filling it: "Do not invent one — a purpose the source does not state is a question for the person."

core-2 puts expectation on the reference instance ("It says how many targets it expects; that gives a miss its meaning. Zero against exactly-one is a defect"). live_docs puts it on the kind, where it is the same for every instance and the author cannot forget to write it. Both are right about different things: an instance-level expectation says "this particular derivation needs these premises"; a kind-level one says "every decision needs a why." For core-2's practical model (the outline's promised rows, the slot declarations), the kind-level form is the one that makes the why-chain a computed owed item without an author having to write a reference to something that does not exist. The AAT analog is a claim kind that expects at least one predicated-on reference, with the miss owed.

### 2.7 Realization: a dimension against an external artifact at a version

**Verified.** `sync-realization` (added 2026-10-06): "the implementation decides realization; the doc never does." It walks every realizable doc in scope, checks the code roots, writes `realization`, `realization_refs` (anchors: path, `path#symbol`, URL, `<root>:path` across repos) and `realization_verified` (the commit when every anchor sits in one clean checkout, else today's date), with a `--note "realization <previous> → <new>: <evidence>"`. It never alters a claim; a claim the code contradicts is reported as drift with the doc's intent and force beside it. `unassessed` means "nobody has checked." `deferred` "never counts as drift": "the person decided not now."

**Bearing on core-2.** This is one of core-2's five-slot dimensions found in the wild, with every slot filled: asks "does the thing exist in the implementation"; of goal/use-case/requirement/decision/component (each with its own verb: reached, supported, met, in effect, exists); against the code roots named by anchors; produced by a read-only check by an agent other than the author of the code (not stated, but the skill's whole stance); read as latest outcome with the stamp telling the reader how fresh. `unassessed` is core-2's *never asked*. `deferred` is core-2's **acceptance with a reason** worn as a value of the dimension, which is a clean way to render acceptance on the line ("· deferred") that core-2's practical model could borrow. And `realization_verified` is the act binding to a version of something the store does not hold, core-2's ‹outside·change› made ordinary.

### 2.8 The changeset carries its reason; the reviewer reads reasons, not diffs

**Verified.** `--note` on the mutating command is the author's explanation of one write; obvious operations auto-fill (`new`, re-parent, `unlink`, `rm`); a revision (body / label / title / summary) must carry an author note, enforced at `session close` (one note per doc suffices; auto-notes never discharge a revision). `session summary` is the agent's recap of the whole episode, "the equivalent of a commit message / PR title," and it heads the review. `20260616181728` (Review the Summary): "Reviewers read a change **summary** that states *intent*, not raw diffs — the same way a pull-request description, not the patch, is the primary review surface." The review lists each touched doc's line (with live facets) and its note, filed once under its dominant change type (deletion > addition > revision > restructure > organizational, computed from which field moved). The raw WAL rides in the review as a non-rendered block.

**Bearing on core-2.** core-2's «changeset» carries no reason and «act» records a criterion and outcome but the def says nothing about a reviewer's surface. `log.kdl` has `did` and `why`, which is the right instinct at the directory level. live_docs' experience is that the *why* on each write is the thing a human can review in bulk, and that the one place to force it is the moment the changeset closes, not per write (per write only nags). For the practical model: a segment changeset wants a note; an atomic changeset wants a recap; and the thing put in front of the steward at a checkpoint is the list of segment lines with their notes, plus the acceptances, not a diff. live_docs also found a small thing worth keeping: the change type is computed from which field moved, never typed, so a review never relies on an agent's self-classification of what kind of change it made.

## 3. Failures live_docs met that core-2 has not yet thought about, or has only named

The ledgers are the best material in the repository: every skill fix records the failure (quoted from a real run), its class (A: information missing; B: the skill's text permitted the bad reading, with the sentence quoted; C: the owner promoted it to an invariant), the diff "placed at the point of highest leverage — immediately after the phrase that most directly permits the bad reading," what was declined and why, regression answers per known-good property, and a ping-pong check against earlier entries. The methodology is adoptable as-is; the specimens are the finding.

- **Over-deference to recorded standing.** The whole October facets redesign exists because of this (Samuel, 10-06 raw): "I was sick of having coding agents refusing to make iterative changes because 'Sinai had ratified the shape' … so I started pushing harder and harder for 'no implementation details' … there's also a silliness there." The result is a model in which "a stored claim informs the next change; it does not restrict it" (`20261006190940`) and no verdict ever refuses or pauses. core-2 has refusals for changeset structure and never for standing, which is consistent, but it has not said what live_docs learned the hard way: minds will treat *ruled*, *ratified*, *exact* as locks unless the practical model says plainly that any changeset may lower or replace an assertion with a recorded reason. The gap row "what agents will do to make the frontier empty" has a twin: what agents will refuse to do because the frontier is empty.

- **Pause-gate rubber stamp and conservative punting.** `apply-to-docs` once paused on impact *size* and asked yes/no to do what the user had just asked (ledger 07-23: "trains the user to type 'yes' without reading"); an agent later handed back a doc contradicted by settled authority as "out of scope, worth a separate look" (08-25: "nobody should have needed to ask"); a 10-13 run asked the owner whether a sentence "needs your call" (10-14). The rule they arrived at (`apply-to-docs` Step 8, "What may go to the person"): anything sent to the person "must carry something only they can weigh: a consideration — a reason, cost, constraint, or use-case — that the request did not take into account, stated in the subject's own terms … 'Doc X says Y' … carries none of that." core-2's frontier "is addressed to someone"; live_docs says what the message to the steward is allowed to contain. That filter belongs in the practical model.

- **The argument register concealed a factual error.** Three ledger iterations on one day (08-24): docs came out oracular ("gold that guesses permanently mislays the finish line"); banning the diction produced manifesto-shaped rewrites; banning the shapes left "polished pomposity"; the root was stance — "docs were written as *arguments* … where documentation should *describe* who does what." The line to keep: the argument register "concealed a factual error … through synthesis, two style passes, and two close readings" because an abstract claim "can contradict a neighboring doc with nothing concrete to check it against." For core-2's fidelity and coherence dimensions: description is what makes a contradiction between restating pieces visible; argument hides it. The acceptance test they landed on is usable as a dimension's *produced by*: "a reader with project context but without the design conversation can repeat the mechanism back after one read."

- **Mechanism narrated as doctrine; unowned disagreement.** (10-14, synthesize-doc-changes and audit-docs ledgers.) Three docs each narrated token issuance from its own vantage; no decision owned the mechanism; an auditor reported the drift as a contradiction and proposed a passing version that *picked* one. Owner's ruling: a mechanism sentence in a non-decision body is read downstream as a decision; disagreement between two non-owning narrations is over-specification, "removed from each; do not arbitrate, and do not ask the person which is right"; and the general form, "a body states as fact only what its own claim asserts. What another doc claims is reached by a link to that doc, never restated here as fact." For core-2's `restates` kind ("the two must agree") this is a sharp distinction: two pieces restating a third that owns the claim must agree *with the owner*, and the repair for their disagreement is to stop restating, not to reconcile them.

- **Owned claims linked, not restated.** (07-28.) Removing one member from a catalog cascaded prose rewrites across every dependent that had restated the member list; the fix was the "restated-ownership repair": collapse the copy to a link to the owner and never sync the copy. core-2's intake segment already warns about a related shape (gold-lift bullets). The rule is general enough for the practical model: an enumeration has one owner; everything else references it.

- **Reachability of the discipline is a property of the graph of skills.** (08-10.) An agent ran the orchestrator but performed a sub-skill inline instead of invoking it, "and therefore never read `label-title-summary.md`, `domain-tagging.md`, `doc-style.md`, or `belongs-to-placement.md` — all four are referenced from `synthesize-doc-changes` and from nowhere else in the pipeline." Fourteen malformed docs; "the store validated clean throughout"; "the same feedback they give every agent on its first ldoc writes." The structural reading: a discipline file reachable from one place is invisible to every agent that shortcuts that place; and green validation is shape, not content. For core-2's practical model: whatever carries how a mind writes a segment or records an act must be reached from every path that writes, or be a refusal in the tool.

- **Typed state drifting from computed evidence, left standing.** The `⚠ DRIFT` instrument is honest and the right shape (a typed flag and a computed fact shown together with their disagreement named), and 32 of 41 raws have shown it since the mechanism landed with nothing draining it. It is the clearest small specimen of why core-2 computes the inbox and source retirement rather than typing them, and equally of what happens to a computed owed item with no checkpoint to force its repair or acceptance.

- **Session fragmentation.** The in-flight changeset's identity is ambient (`LDOC_SESSION` in the shell; the record on disk keyed by id, never a shared "current session" file because concurrent sessions in different shells would conflate it). Agents forget to export the id, each `ldoc` process is separate, and the result is several one-command sessions, reconciled afterward by `session merge` into the earliest. `20260701203750` is the decision and `20260701224959` the accident guard (re-opening over a live session is an error). This bears directly on core-2's "a working state belongs to one atomic changeset" and on the `CC_AGENT` work: the atomic changeset's id must reach every mind and tool acting in it without being threaded through arguments, and fragments will happen and need a fold.

- **What `map` shows decides what agents learn.** (07-17 raw, Samuel.) He omitted reference docs from the viewer but not from the CLI, then saw what an agent would get running `ldoc map` in his other store: "most of what I saw was a huge list of reference docs (because they were 'global' cause they weren't 'scoped', cause I didn't worry about organizing them because they're not important). This is super problematic … I had been thinking that those were just 'nice to have' things; but I'm now realizing that this is actually critical for certain aspects of the CLI; because that determines what gets explored or learned by agents using this system." The resulting rule (`20260717210143`, Footnote-Grade References, a `must`): reference material has "prominence … equivalent to a footnote backlink," omitted from `map`/`ls`/`orphans`/`validate` by default and ranked last in `find`. core-2's inbox and sources sit outside what a segment says; live_docs says they must also sit outside what the orienting surface shows.

- **An immutable snapshot inside a mutable changeset.** (07-22.) `session close` tried to write a creation history entry onto a reference doc created mid-session; reference docs refuse history writes; close failed on the happy path (apply-to-docs creates such a doc in Step 1b). Fixed by skipping materialization for archived docs while the review still records them from the WAL. For core-2: a ‹source› segment and its chunks are written once and never changed; a crossing act touches a chunk without writing it; the changeset that lands the source must not be refused for failing to "affirm" a source's inner dependents. Small, but it is the kind of seam the first real run will hit.

- **Hot files as a recut signal.** `20260615203928`: history length above a threshold (five entries, mixed-topic notes) is a first-class decomposition candidate; creation entries are excluded from the count. core-2 discovers grain by adjudication (a check narrows part of a piece); live_docs also discovers it by churn. Both are "grain found after the fact," and the second detector is cheap.

## 4. The practical model: affordances a mind at work meets in live_docs

Grouped by what core-2's verisectorium def names: the outline, document-like segments, the inbox, the frontier, the checkpoint, and what each wants. All verified in skill text or by running the command unless marked.

**The line.** Every surface that lists docs (`ls`, `find`, `map` with children, `neighbors`, `graph`, `log`, review bodies at render time, `hierarchy.md`, the MCP tools) renders a doc as `<Intent> <type>: <Title>` with ` · force · realization · flagged` trailing; a deprecated doc is struck through and names its successor; a doc with no intent reads "Unattributed" and ranks with incidental. Ranking everywhere is status (living, deprecated, reference), then intent (requested, chosen, incidental), then the surface's relevance; archived material is omitted by default or last. `ldoc cite <ref>` prints the line as a markdown link into the viewer, and the skills require every report to name docs that way, "never by a phrase of your own, and never by its id alone in prose." Samuel's reason (10-06): "'Decision #30' looks important and enforceable and like gospel truth; but 'Deprecated: ~Decision #30~' doesn't, nor 'Incidental: Decision #30'." This is the rendering of standing core-2's inline row "rendering" gestures at, made into a rule: the standing is on the line, leads with who stood behind it, and the same line is the citation form.

**The three descriptors.** `label` (2–5 words Title Case, unique, the resolution handle; must name the subject, "not be a label of the answer" — `Retry Backoff`, not `Retries Wait Exponentially Longer Between Attempts`; no meta suffixes like "Mechanism"); `title` (optional sentence-length elaboration, defaults to the label); `summary` (1–3 sentences, ≤ ~50 words, "shown verbatim in reviews, search results, and index maps," distilled "by selection, not compaction," validate warns above 60 words; a whole-corpus re-summarization was done once, 2026-06-18, "avg now ~41 words"). The vocabulary rule: prefer the person's words; "an agent-coined name that does not appear in the source is a proposal."

**The outline.** live_docs' outline is the `belongs_to` hierarchy, and `ldoc map` renders its roots (biggest subtree first) with summary, child count, scope and the direct children. Membership is written on the child only ("Membership points UP"), so the parent carries no list, and the parent's body is a synthesized **orientation guide**, re-run by `garden-summarize` when a member changes substantively (cascade's "descendant-summary rule"): "Synthesize, do not concatenate. No `## Map` or member enumeration — membership lives in edges." Placement carries meaning: a decision binds the subtree it is placed under and is global when unplaced; effective scope is the union of `scope` anchors along the ancestry (`20260619235018`); the tree is kept "roughly balanced, width proportional to depth," with ≈12 direct children as a trigger to examine (not to split) a branch. A `heading` type (added 10-07 after a negotiation preserved in the raw) is the claimless parent and the only type exempt from carrying a why; any other type may still head children. Signposts are structural (having children), never a type. core-2's projection def leans toward "a projection kind may declare content slots of its own beside its member slot; the preface is then its veritoid" — live_docs has run that shape for four months and confirms both halves: the preface is authored content that goes stale when members change, and the member list must not be content.

**Document-like segments.** One claim per doc; body ceilings per type; the body states the claim and its why and nothing about history, absence, deferral, or mechanism; implementation detail has two legal homes, `realization_refs` and a volatile `## Implementation` section; "the body is not a changelog" (what changed goes in the `--note`); "clarification shortens a doc" (a revision that grows must say why in its note); a `## Correction` section is the one thing added to a deprecated doc. The why-chain per type is expected and warned. Deletion is the default retirement ("if removing the doc loses no information, delete it"); deprecation (status + `superseded_by` + Correction) is for an overturned belief whose record has value; `superseded_by` on a *living* doc is planned succession (current path and planned replacement coexist, both living). Reference docs are immutable through the porcelain ("delete and re-ingest if the snapshot is wrong").

**The inbox.** Three stages, two gates: `inbox add` (instant, verbatim, provenance flags `--origin --medium --authored-at` carried losslessly), `promote` (a human's acceptance into the immutable raw tier, outside the graph), `ingest-reference` (decomposition into claims; "a blob ingested as a single doc is a liability"; the normalized reference doc is the provenance anchor every extracted claim points at). Gate 1.5, `shard-clipping`, splits only on concept volume (~50 atomic docs) and only into verbatim gatherings with full coverage ("Divide the unit of work, not the phases": comprehension and synthesis of one unit are one act and a plan/apply split loses the nuance either way). `raw list` shows pending / ingested / sharding / sharded with the DRIFT cross-check. Three timestamps are kept apart: authored, captured, imported. Against core-2's intake segment: the normalized reference doc is a piece core-2 does not have (a frozen summary of the source *inside* the graph), the ingest extracts concepts rather than cutting a covering set of chunks (only shards must cover), and nothing records where each chunk went — the raw is marked ingested whole. core-2's per-chunk ‹crossing› with outcomes is finer; live_docs' reference-doc-as-anchor is a practical convenience worth weighing (a source's summary that claims nothing and is cited by everything extracted from it).

**The frontier as it exists here.** `ldoc validate` is the frontier: errors (shape the tool would refuse to write: forbidden facet, `requested` without basis, broken hard edge, deprecated without successor, `belongs_to` cycle, duplicate label, heading with no child) and warnings (content the kind expects: missing facet on a legacy doc, missing why-chain edge, `tradeoff` without its upstream, body over ceiling, prose link not edged, summary long, obsolete `level`/`target`). Each warning class has a named phase that works it (`garden-densify`, `-refine`, `-decompose`, `-integrity`). `flag add <ref> --reason` is the reader's one write: a mid-task reader records that a doc is badly written and moves on; the doc's line gains ` · flagged`; `map` and `validate` end with the open-flag count; `/garden` drains flags before any other signal; a rejected flag must be resolved with "the standard the doc meets and how." The `cruft-verdicts` rule generalizes it: "A signal decides the verdict … KEEP on such a doc says the signal was wrong, and names the standard the doc meets." That is core-2's "a deliberate decision not to raise something is itself an attestation, with its reason," made into a queue with a drain.

**Where the checkpoint would be.** There is none. What stands in for it: `session close` (blocks only on missing revision notes, mints the review), the signed review (post-hoc, optional, batch-signed), `validate` (reports), and git. `ldoc edges --json` reports dangling edges store-wide before a cascade walk. Dry-run previews of mutations emit "the same review-summary artifact the mutation would generate" (`20260616200145`) so a reviewer reads one format for past and future changes.

**The act layer, as skills.** The judgment is in prose procedures, deliberately: "mutators are dumb; judgment lives in the skills." The orchestrators (apply-to-docs, ingest-reference, revise-doc, reconcile-changes, garden) share phases as `user-invocable: false` sub-skills (identify-key-concepts → map-concepts-to-docs → assess-blast-radius → synthesize-doc-changes → cascade-check), with the rule that shared *procedure* is a sub-skill and shared *definition* is a prose include every writer reads (`20260624172737`). Every write-making episode is one session and one review; nested phases never open or close one. Cascade is two strict passes (read-only verdicts over the whole reachable set, then one batch write), with "inconsequential" as the explicit norm, "context-request" when impact cannot be read, and a wide-cascade smell (> 3 docs from one edit) routed to gardening as a single-responsibility signal. `audit-docs` (10-14) is a read-only independent read of a change set by "a reader who has not seen the request," blind pass before sourced pass, five-part findings with the governing section cited — a cold read as a standing skill. `garden` is a thin dispatcher over phases ordered by antagonism (cruft → decompose → collapse → hierarchy → domains → densify → refine → integrity; "there is no point splitting a doc about to be excavated, or merging one about to be removed"), with a guard against decompose/collapse oscillation inside one episode, and sampling QA (`garden-refine`, 10–20 docs biased to recent and never-refined) on the principle that "agentic pipelines produce sporadic inconsistency; sampling is the correct response." Domain tags are a "finite shared resource" originated liberally in isolated context and pruned authoritatively with full-store context.

**The viewer.** A self-contained HTML export with Dashboard, Reader (hierarchy sidebar, focus pane with connections and a collapsed history timeline, edge-aware neighborhood graph), Catalog (facet table, click-to-filter), Reviews (a sign-off queue; unsigned cards marked; integration counts per review: new-to-new, new-to-existing, edges-added-to-existing, "did this session create an island of new docs, or did those docs tie into the store?"), and Lexicon. Not read in depth; its page list verified by grep.

**The lexicon.** A sibling box of human-ratified terms, identity = the term slug (no ids; "a rename is a different term"), `{{Term}}` soft links that may be broken on purpose ("linking a term that does not yet exist signals it should be documented"), outside the graph, no status, no cascade, no history. Worth a glance against core-2's `avoid` lists and the "names are the interface" understanding: Samuel keeps the vocabulary as a store, adjacent to and softer than the claims.

## 5. What live_docs holds for core-2's named gaps

Short, because most of these are "they met it too and did X" rather than answers.

- **Write-time addressing.** Sidestepped by one level: a ref is `id | label | unique substring`, and agents never type ids (`ldoc resolve`; bare `[[id]]` in bodies expanded at render). The cost of one level is in §2.5. The `## Implementation` exemption and the body ceilings are the pressure the missing level exerts.
- **Ontology change record.** The facets migration (10-06) was recorded as decision docs in the KB (`20261006190929`–`190952`), a one-shot script (`migrate_level_to_facets.py`), a judgment session recorded as a review with a per-doc note on each of 55 restructured docs (`20261006192312`), and a tolerance rule: "loose on input and strict on output" (`20261006190937`, a `must`) — old fields are read and ignored, expected-but-missing fields warn, writes refuse. `TYPE_TABLE` in `model.py` is the one copy of the ontology; the shared `_shared/doc-types.md` restates it in prose for agents, which is a duplication they accept. The kind change lapsed nothing; it produced warnings. That matches core-2's lean ("an act binds to versions, not to kinds, so a kind change lapses nothing by itself") and shows the warning-not-lapse form working.
- **The recording cost.** Their answer is `--note` inline on the write (auto-filled where obvious, required for revisions, enforced at close) and "make stating the act be recording it." Four months of real use at doc grain: 277 docs, 76 reviews, 141 docs with three or more history entries. The cost that was *not* paid is in the intent numbers: evidence for standing was recorded on 52 docs and 225 remain Unattributed. Recording a write's reason is cheap; recording the evidence for standing is not, even at doc grain.
- **Refusals.** §2.2 and §4 (frontier): refusals for shape at the write (`new`/`set` refuse a facet the type forbids, an intent without basis, a missing label; `rm` refuses with inbound edges unless `--force`; archived docs refuse mutation), one refusal at the changeset boundary (`session close` without notes), and never a refusal about content truth. The dry-run channel refuses "exactly what the real write would." That three-point placement is a worked answer to the gap row.
- **Parallel changesets.** Concurrent sessions are allowed (the ambient pointer is per shell); writes land immediately; there is no merge semantics and no notion of two steady states combining. Punted to git, as core-2 punted.
- **Independence of acts.** Nothing. Signer ≠ author is not checked; Samuel signs his own agents' sessions. The earlier design doc's "signer ≠ WAL author" was a proposal.
- **Steward attestation.** §2.2.

## 6. Corrections to the summary the brief carried

The brief listed what the early notes found in live_docs via the August design document. Three of those items were that document's *proposals* for live_docs, not things live_docs does, and should not be carried forward as live_docs practice:

- **"Signed reviews that decay on later edits."** live_docs has no decay. Signoffs are permanent `{who, at}` entries appended to the review file (`reviews.py` read whole; `grep -n decay` over `ldoc.py` and `livedocs/*.py` finds only a graph-layout alpha in the viewer). Decay-on-edit was §7.2(4) of the August document.
- **"Queues surfaced at session close."** `session close` prints the session id, review id and path (verified in `cmd_session`). It blocks on missing revision notes and on nothing else; it shows no unsigned reviews, no drift, no warnings. The only queue footer anywhere is the open-flag count on `map` and `validate`. Surfacing queues at close was §7.6 of the August document.
- **"Signer ≠ author."** Not checked anywhere; a proposal.

The other four were accurate: the session WAL as the unit of change; per-doc history as a projection materialized at close; the two-pass cascade; navigation (`belongs_to`) kept apart from dependency (`requires`).
