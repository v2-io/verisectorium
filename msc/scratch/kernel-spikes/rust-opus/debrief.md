# Debrief: the kernel in Rust (Opus 5.5)

Joseph, this is for you. The full account, with the proof table the four spikes share, is `account.md` beside this file.

## What exists

A Rust library that holds a log of two kinds of record: a segment's new written state, and an act (a check, or an author's affirmation). It computes, from any prefix of that log, which acts still bind, each piece's position and ceiling, the frontier of what is owed, and whether the store is steady. Nothing it reports is stored. A small CLI writes and reads the log as plain text. The spec's worked example runs end to end and reaches the steady state the spec promises.

## What it found about the spec, which is to say about the model

**The worked example's expected frontier is wrong, by the spec's own definitions.** After the root claim c changes, the spec lists seven owed items. Running its own definitions over every piece gives nine. The description e now overclaims (it claims drafted, and nothing under it supports more than sketch); d and e both have an unmet need on c. One listed item, "d's reference to c is stale", cannot be owed, because d was rewritten against the new c in the same changeset. The list looks hand-assembled by asking who points at c, and that is the very failure a computed frontier exists to prevent. A test pins the difference exactly.

**An affirmation that does nothing makes the example's ending impossible.** The spec says an affirmation never counts toward a rung, and gives it no other effect. Then e, never rewritten, stays "written against the old c" forever, and the store never becomes steady. I gave the affirmation one effect: a binding affirmation reconciles the affirmed piece's references to what it read. It still never raises a rung, and it lapses like any act if either side changes again. With that, the example ends exactly where the spec says it does. This matches your model's own definition of a segment changeset (every dependent "either changed or carried with the author's affirmation").

**The act needs a "what it attests" separate from "what it read".** The spec raises the position of everything an act read. A re-derivation of u must read u's premise c, so recording that honestly would certify c, which nobody checked. The spec's own example therefore records the check of u as reading only u. The cost is quiet: when c changes, u's check doesn't lapse, and u keeps "rederived" on work done against a premise that no longer exists. Your act definition says recording too little is as dishonest as claiming too much; the spec's shape forces recording too little. I added `concerns ⊆ reads`: binding uses everything read, and position counts only what is attested.

**A version number has to mean one content for the life of the store, or old checks come back to life wrongly.** Whether an act binds depends only on current versions, so reverting a piece to an earlier version revives every check of that version. With content hashes that is correct and rather elegant. With counters it is a hole: remove a piece and re-add it at an old number with different content, and the old checks revive on content they never saw. My first version of the kernel had this hole for references, and a property test I wrote to state the invariant found it. The kernel now refuses any reuse of a version with different references anywhere in the log's history. It cannot see the content itself, so I'd recommend the model require content hashes and make this a fact instead of a promise.

**Two smaller things worth your judgment.** First, only writing ever adds to the frontier: no check or affirmation ever adds an owed item (tested; a bounded proof was attempted and did not finish). Second, the "needed rung" on a reference mostly duplicates the ceiling. Whenever the needed rung is at or below the piece's own claim, an unmet need already implies an overclaim. The ceiling ignores the needed rung entirely, so "d needs c only at drafted" never lets d rise above c. Either "needed" means something the ceiling should consult, or it is a separate assertion whose job the model hasn't said yet.

## What Rust was like, and what got proved

**Writing the kernel was nearly free.** The whole thing, with the CLI, the worked example and tests for all eight properties, was committed nine minutes after I started, and it compiled almost first time. Rust's enums let the code say what the model means, so mistakes can't be written. An affirmation has no rung field at all, so nobody can attach one. A refusal or an owed item of a new kind is a compile error everywhere it isn't handled yet. The log can only be appended to: privacy makes that true for every value of the type, and the compiler rejects the specific violations I tried.

**Testing was where the work and the value were.** Every property is tested against 1024 generated logs, compared with a second, naive implementation written straight from the spec's text. A coverage test fails if any interesting case stops occurring, and that test is what caught my first generator producing tests that passed by never exercising anything. I seeded 20 deliberate bugs into the kernel and the tests caught all 20.

**Proof: none completed.** Rust's practical route to proof on the actual shipped code is bounded model checking (Kani). Kani spent its entire budget inside the standard library's B-tree and string code, before reaching the kernel's logic. I made two concessions, both confined to verification builds: small integers for ids, and a simple sorted-list map in place of the B-tree. Even then, no run finished in 10–18 minutes, and all were stopped (the last batch because, together with the other Rust spike, they were starving the machine; I should have asked before running four at once). An unfinished run is evidence neither way. The unbounded route (Verus, Creusot) means rewriting the kernel in a verification dialect, which I didn't attempt. My estimate is hours for the easy properties and days for the graph ones.

So, from this side of the comparison: Rust made it fast and pleasant to *build* the kernel correctly, and to *test* it hard. It did not let me *prove* it, in the time and on the machine I had. If the Ada spikes report contracts discharged on their shipped code without heroic effort, that is the gap. I can't judge their cost from here.

**Did I get the proof that matters most?** No. The property that would most change my confidence is that a check stops counting exactly when something it read changes, together with the fact that only writing ever adds debt. Both are tested strongly, and neither is proved.

**Where things are.** `account.md` has the per-property proof table asked of all four spikes, every decision and finding with the test that pins it, and the timeline. `tests/worked_example.rs` holds the spec discrepancies as executable facts. `kani-logs/` holds every attempted proof run, named by how it ended.
